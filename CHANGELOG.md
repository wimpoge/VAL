### `start-all.ps1` — em-dash inside string literal broke dot-source

- User reported `. .\start-all.ps1` failing with `The string is missing the terminator: "` at line 107 char 83, plus `Missing closing '}' in statement block` at line 94. False-alarm dismissal in the prior changelog entry was wrong — my AST-parser test loaded the file via `[Parser]::ParseFile()` (which honors UTF-8), but **dot-sourcing from an interactive PowerShell session reads with the legacy default codepage** (Windows-1252 on most English Windows installs).
- **Root cause.** The line I added — `Write-Step "Practice frontend not found at practice\frontend\ — skipping."` — contained an em-dash (`—`, U+2014, UTF-8 bytes `E2 80 94`). Decoded as Windows-1252, those three bytes become `â€"` — and the trailing byte `0x94` is `”` (U+201D RIGHT DOUBLE QUOTATION MARK). PowerShell's lexer **treats curly quotes as equivalent to straight `"` inside expandable strings**, so the parser saw `"Practice frontend not found at practice\frontend\ ”` as a closed string, then read ` skipping.` as bareword tokens, then `."` re-opened a new string that ran until EOF — hence the cascade of errors blaming lines 94 / 107.
- **Fix.** Replaced all three em-dashes in [start-all.ps1](start-all.ps1) (one in the string literal at line 95, two in comments at lines 68 + 87) with ASCII hyphens. The comments would probably have been tolerated by the parser, but I converted them too for consistency — and because PowerShell occasionally surprises you in strings that *aren't* obviously strings.
- **Verified by running the same code path the user did.** `Get-Command -Syntax .\start-all.ps1` (which loads via the default codepage, same as `.` dot-sourcing) now succeeds; AST parse also clean. [stop-all.ps1](stop-all.ps1) had no non-ASCII characters to fix.
- **Forward rule:** plain ASCII in `.ps1` is the safest default. If a future script genuinely needs Unicode characters in string literals, save the file as UTF-8 **with BOM** so the PowerShell engine auto-detects the encoding instead of falling back to Windows-1252.

### Day 10 / N49 — vision URL pipeline now server-fetches the image

- Live `/day10/describe-image` against the original Wikimedia preset URLs failed with OpenAI's misleading `BadRequestError: You uploaded an unsupported image. Please make sure your image has one of the following formats: ['png', 'jpeg', 'gif', 'webp']`. Root cause is not the format — OpenAI's downstream image fetcher gets blocked / hands back HTML on hosts that User-Agent-gate (Wikimedia's `upload.wikimedia.org` thumb redirector is the classic offender; quick `httpx` probe with even a friendly UA returned 400 + HTML).
- **Backend fix.** New `_fetch_image_as_data_url(url)` helper in `routers/day10.py`. Uses `httpx.Client(follow_redirects=True, timeout=15.0)` with a real `Mozilla/5.0 (compatible; ValBot/1.0; +<repo>)` UA and `Accept: image/*`. Validates `Content-Type` against `_ALLOWED_IMAGE_MIMES = {image/png, image/jpeg, image/gif, image/webp}`, enforces the existing 4 MB cap, then base64-encodes into `data:{mime};base64,…`. Maps network failures to 502 ("could not fetch image: …"), non-200 status to 502 ("image host returned HTTP X"), wrong content-type to 400 with the allowed list, oversize to 413. `describe_image_url()` now calls `_fetch_image_as_data_url(url)` and hands the data URL to the existing `_run_vision()`, so the URL and upload paths both reach OpenAI as data URLs through the same code path. Pulled `httpx` into the module imports (already in `requirements.txt`).
- **Frontend fix.** Swapped the two Wikimedia preset URLs for three reliable-against-bots hosts: `https://picsum.photos/seed/val-cat/640/480`, `https://picsum.photos/seed/val-mountain/640/480`, and an Unsplash photo. ### Day 9 — AI Agents (N41–N45)
